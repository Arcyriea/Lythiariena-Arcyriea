2. Current player initialization flow
Game constructs ObjectPool, EntityManager, FactionManager, ShipManager, and ProjectileManager, then calls loadGameData() in Game.ts.
loadGameData() clears shipData, sets the PlayerCannon tuple, calls ShipDataAdapter.ingestLegacyData(), then registers the player as a structured legacy blueprint with gameplay.parts, gameplay.components, stats, and visual sprites. Finally it syncs any remaining legacy ship definitions (Game.ts).
GameScene.create() reads those legacy visual sprites to build the Phaser player Container. It creates the Arcade Physics body with world-bound collision disabled and drag 200, configures input, then acquires the logical player through ObjectPool.getShipObject('player') (main.ts).
The scene assigns the player faction and Phaser position, rotation, body and scene references; registers the ship with EntityManager; and stores the Container as ship.sprite. It does not add the player to Game.shipQueue (main.ts).
Each frame, the scene handles the existing steering and acceleration, copies Container state to the logical ship, updates its components, and activates its weapons on pointer click. Game.update() handles the rest of the game loop (main.ts).
The camera follows the Container. On scene shutdown, the player is unregistered, its faction is cleared, it is returned to the object pool, its Phaser back-references are cleared, and the projectile manager is unbound (main.ts, main.ts).
The player therefore has a deliberate scene-owned path separate from ordinary managed ships. The migration should keep it.

3. Existing canonical infrastructure
The corrected audit’s key claims are supported by the source:

Shipmaker.ts already defines hull parts and mount contracts; it also defines HullDefinition, canonical weapon component types, ShipLoadout, and the canonical ShipBlueprintDefinition.
Game.ts already owns typed hull, component, loadout, and legacy-compatibility registries.

Legacy weapon projections create hardpoints that accept both spinal and turret weapons; those projections are compatibility data, not authored canonical player definitions.
Ship.init() selects its canonical path when the registered blueprint has hullId and loadoutId. That path resolves hull and loadout, materializes hull parts at their declared coordinates, processes built-ins, rejects duplicate or reserved installations, checks mount compatibility, and creates installed components (Ship.ts).
Canonical component installation already reaches Component.init(), which distinguishes canonical definitions from legacy definitions and tuples. Canonical weapons are initialized by Weapon.init(); when the game has a projectile manager, Component constructs a ManagedWeapon (Component.ts).
Canonical definitions in shipmaker-parity.test.ts are manually registered after game setup. They are distinct from adapter-generated legacy records and the still-legacy production player.
4. Exact migration gap and risks
The current player blueprint has neither hullId nor loadoutId, so Ship.init() selects the structured legacy branch. Its component tuple becomes an adapter-produced kind: 'legacy' record, and its cannon is attached by legacy partIndex.

The migration can use the canonical path already in place, but ordering matters: authored canonical player definitions must be registered after ingestLegacyData(), because a later ingestion clears and repopulates the registries. Re-ingestion after authoring would erase the canonical records and recreate the legacy PlayerCannon record. No adapter changes are required if player definitions are registered after the one existing ingestion call.

There are no non-test production references to PlayerCannon beyond its tuple and the player attachment in Game.ts. Tests have their own legacy tuple fixtures. Removing the production tuple and registering a canonical PlayerCannon avoids having the same ID act as both the production legacy tuple and canonical definition. The adapter should remain available for other legacy content.

Important visual dependency: after migration, the player definition will be canonical and no longer have the legacy visual field. The current player setup in main.ts requires that field and would throw. The scene needs to obtain the existing player sprite descriptors separately.

Firing compatibility: both weapon paths compute projectile origin from the installed component’s shipPart position rotated by ship angle, and use ship angle for direction. They inherit Phaser body velocity; the managed path also captures source ID and faction through ProjectileManager (Weapon.ts, ManagedWeapon.ts). A hardpoint at (0, 0) therefore preserves the current player’s center origin and ship-facing direction. Although canonical contracts include attachment and muzzle geometry, these firing implementations do not consume them. An empty muzzle list and no invented muzzle geometry are sufficient for this migration. Configured range and splash radius remain 400 and 0, but the current Arcade projectile path does not apply range or splash behavior.

The canonical Component.subType will be the component ID rather than the legacy firing-mode string. I found no production consumer of a weapon component’s subType; firing dispatch uses the weapon effect’s firing mode. Existing tests that assert legacy subtype should assert the canonical weapon’s firing mode instead.

Ship.hullDefinition is set by canonical initialization and cleared by reset; its runtime consumer is hull-mod capacity (Ship.ts). Pool acquisition calls Ship.init() for both new and reused ships (ObjectPool.ts); initialization resets stats and collections, and disposal clears the hull reference. No pooling change is indicated.
