3. Four-bundle architecture and source discovery
Agreed organization:

No numeric suffixes or combined nonships.bin are permitted.

The packager should scan immediate child directories under private/assets/, recurse within each category, and reconcile every supported file against exactly one registry entry. The folder determines bundle grouping; the registry supplies identity and runtime metadata; the packager validates and produces bundles; the generated manifest records derived bundle IDs, filenames, membership, and fingerprints. The listener, when added, will coordinate this same packager rather than implement packaging independently.

Naming recommendation: accept ASCII category names composed of alphanumeric groups separated by spaces, underscores, or hyphens; lowercase them and normalize separator runs to -. Reject non-ASCII names instead of transliterating them. Detect normalized-name collisions before output changes and fail rather than add suffixes. This preserves current names and makes future naming behavior deterministic.

Behavior for discovered content:

.svg and .png are the only supported source extensions in this phase; each must match its registry contentType and pass format validation.
JSON and unknown content types remain unsupported, even though JSON is enumerated in RTAB v1.0.
An unregistered SVG or PNG fails explicitly; the packager never invents IDs, keys, or aliases.
A registered but missing source fails; there is no public-file fallback.
Any unsupported file inside a category fails with its path rather than being silently ignored.
An empty category directory produces no bundle. A registered asset missing from that directory still fails reconciliation.
A new category produces a bundle only when it contains registered supported assets. For future categories, allow registered SVG/PNG files without adding a category-specific packaging rule. For the four current categories, enforce the stated SVG/PNG expectations.
Reject path traversal, duplicate logical paths, case-insensitive collisions, symlinks/reparse points, unsafe category names, and output path collisions before publication.

6. RTAB v1.0 SVG and PNG handling
Keep the existing RTAB v1.0 format unchanged: 64-byte outer header, 28-byte index header, 72-byte records, SHA-256 payload/index digest semantics, and compression method NONE.

SVG keeps the existing UTF-8 XML, well-formedness, and SVG-root validation and preserves exact source bytes.
PNG stores the original source bytes without image decode/re-encode and without another compression layer.
RTAB record content type is 0 for SVG and 1 for PNG. Both payloads use the current SHA-256 process over exact bytes.
PNG validation should cover the actual structure, not the filename: signature, first and unique IHDR, valid nonzero dimensions and legal IHDR fields, bounded chunk ranges, CRC for every chunk, required IDAT, required/valid PLTE when indexed, valid chunk ordering, zero-length IEND, and no bytes after IEND. Reject unknown critical chunks. For robust validation, also validate the IDAT zlib stream and scanline structure without re-encoding the image. This introduces a decoded-size/resource-limit policy that should be resolved before implementation to avoid excessive decompression memory use.

Tests must verify PNG bytes survive packaging exactly, and reject malformed signatures, dimensions, truncation, invalid CRCs, bad chunk order, missing required chunks, malformed compressed data, and trailing data.

9. Publication, ownership, rollback, and stale output recovery
Build and validate the complete output set before publishing. Use same-volume temporary files adjacent to outputs, publish bundles/schema first and manifest last as the commit marker, and retain prior outputs for rollback on handled failures.

Overwrite/delete an output only when it is proven packager-owned through a valid previous generated manifest: the path must be confined to public/assets/, the record must be valid, and the file hash/content must validate. Refuse collisions with paths absent from that manifest. Never wildcard-delete .bin files.

The old public/assets/Ships/ships.bin is tracked and currently part of the valid prior manifest. Preserve it until all four new bundles, schema, and manifest validate and publish successfully. Then remove that specific stale path based on the prior manifest ownership. If generation/publication fails, retain the old file and outputs.

Multiple filesystem renames cannot be crash-atomic. Handled failures should roll back; after abrupt termination, the next full preparation must inspect the manifest and hashes, regenerate/repair the complete output set, and only remove stale owned outputs after the new set validates. Ambiguous temporary/backup files must not be wildcard-cleaned.

10. Stage B — Continuous listener, after Stage A review
Implement only after Stage A has been reviewed and accepted. The listener watches .svg and .png additions, changes, deletions, renames, directory changes, and registry edits. It reuses the Stage A APIs.

Debounce bursts, serialize jobs, coalesce changes during builds, and rebuild only one category when a simple registered-file modification is unambiguous. Registry edits, moves/renames, category changes, invalid outputs, or ambiguous events trigger full reconciliation. Every run validates sources and output before publication; failure preserves prior valid outputs and reports the relevant path.

Use Vite’s watcher as the starting point, explicitly test recursive watching and ignored private/ paths on Windows, and do not claim support until those tests pass. Add Chokidar only if those tests demonstrate Vite’s watcher is insufficient. Dispose listeners and pending work on server shutdown. predev and prebuild remain full reconciliation boundaries.

Regenerating bundles does not hot-reload Phaser artwork. Phaser continues loading the loose public images until separately approved Phase 3C integration.
