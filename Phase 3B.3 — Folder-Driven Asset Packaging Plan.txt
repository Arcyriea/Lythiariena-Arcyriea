2. Recommended source of truth and folder discovery
Keep the existing separation of responsibilities:

Private folder structure: determines category membership and bundle grouping.
Registry: owns stable asset IDs, logical paths, texture keys, aliases, and content types.
Packager: discovers files, reconciles them against registered assets, derives bundle metadata, and creates outputs.
Generated manifest: records packaged assets, their derived bundleId, bundle paths, and fingerprints. It remains generated output, not an authoring source.
On a source-available preparation, scan the immediate child directories of private/assets/ as categories, then recursively enumerate supported SVGs within each category. Match each discovered file to exactly one registered logical path, preserving case. Fail before publication for a missing registered source, an unregistered SVG, a duplicate/case-colliding path, a symlink/reparse point, or a category name that cannot produce a unique safe bundle name. Ignore empty category directories; do not emit empty bundles.

The physical category directory is the packaging authority. The corresponding registry logicalPath must agree with the source’s mirrored path; it supplies identity and runtime metadata, not an alternate bundle assignment. For clean-clone validation, where private sources are absent, derive expected category membership from the registered logical paths and compare that expectation with the generated manifest.

Bundle ID and filename normalization
Derive the bundle ID and output path from the category directory name; do not add numeric suffixes:

Category directory	Derived bundle ID	Output
Ships/	ships	/assets/ships.bin
Components/	components	/assets/components.bin
Turrets-Platforms/	turrets-platforms	/assets/turrets-platforms.bin
Future Stations/	stations	/assets/stations.bin
Proposed normalization: Unicode NFKD normalization, remove combining marks, lowercase, replace each run of non-ASCII-alphanumeric characters with -, then trim leading/trailing hyphens. Reject an empty result and detect collisions after normalization before building anything. For example, two differently named category directories normalizing to the same slug must fail, not be suffixed or silently combined.

Also refuse to overwrite a target .bin file unless the prior generated manifest establishes that the packager owns that path. This protects user-owned files that happen to match a derived output name.

5. Stage B — Continuous development listener, separate from Stage A
Do not couple filesystem watching to bundle-format or registry discovery logic. The listener should call the same preparation/packaging APIs; it must not own a second implementation of packaging.

Recommended approach: add a small scripts/watch-assets.mjs coordinator and attach it to the Vite development-server lifecycle through a new vite.config.mjs, using Vite’s existing watcher rather than introducing a new dependency initially. Explicitly add and watch private/assets/ and scripts/asset-registry.json; test that ignored private paths are watched correctly on Windows. Add Chokidar as a development dependency only if Vite’s watcher fails the required platform behavior tests.

On dev startup, perform a full reconciliation before serving changes, then watch for SVG add/change/unlink, directory add/remove, and registry edits. Keep predev/prebuild as full reconciliation boundaries so missed events cannot leave stale production output.

Listener behavior:

Debounce event bursts; serialize rebuilds with a single-flight queue. Events arriving during a build mark the state dirty and schedule one coalesced follow-up.
For a stable edit to a registered asset, identify its category and rebuild that bundle only when the full inventory and registry still reconcile. Reuse unaffected bundles only after validating their existing fingerprints and membership; regenerate the manifest consistently.
Use full reconciliation for registry edits, new/removed categories, moves/renames, ambiguous event batches, or invalid previous outputs. If the registry has not been updated for a move, report the missing registered path and new unregistered path; do not infer IDs or metadata.
Validate source stability before publication. Handle Windows duplicate/rename events, case-only changes, writes in progress, and transient sharing violations without publishing partial output.
Preserve the last valid generated outputs on errors, report the path and reason, and wait for a later event or restart rather than entering a tight retry loop.
Detach listeners and await/cancel queued work during server shutdown.
Watcher output changes do not hot-reload Phaser artwork. Until Phase 3C, Phaser still reads loose SVG URLs; the watcher only synchronizes generated bundles/manifests.

6. Future mod compatibility boundary
No mod discovery, installation, enablement, loading, merging, or override behavior is implemented in this phase.

Keep category-name normalization and grouping independent of the base source root so a later composer can group assets from multiple independently owned source sets by category. Future mod registries should be merged in memory with the base registry, not copied into or written over private/assets/. Reserve a future namespaced ID convention such as mod.<modId>.<assetName>; reject duplicate IDs, texture keys, and aliases by default. Do not support implicit overrides: conflict/override policy, mod-qualified logical paths, and mod manifest versioning require a separate design. Removing a mod later should regenerate combined outputs from remaining sources without modifying base or mod source files.
