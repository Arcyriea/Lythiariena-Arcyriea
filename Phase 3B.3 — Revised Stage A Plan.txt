4. SVG and PNG validation under RTAB v1.0
Keep RTAB at 0x0100, with the existing 64-byte outer header, 28-byte index header, 72-byte records, SHA-256 semantics, and compression = NONE. Store original SVG and PNG source bytes unchanged.

SVGs retain current UTF-8 XML, well-formedness, and SVG-root validation.
PNG content type is 1; SVG is 0. JSON (2) and Unknown (3) remain unsupported.
RTAB record type must match both the corresponding generated-manifest contentType and registry entry. Neither validator selection nor the manifest alone is sufficient evidence of consistency.
Supported PNG profile and resource limits
All five inspected PNGs are RGBA8 and non-interlaced. To keep decompression bounds precise, the recommended first profile supports only bit depth 8, color type 6 (RGBA), compression method 0, filter method 0, and interlace method 0. Reject any other profile from IHDR before invoking zlib. Adam7/interlacing is unsupported in Stage A; it may be proposed separately if required later.

Proposed limits:

Maximum dimensions: 4096×4096.
Maximum compressed bytes: 8 MiB per file; 32 MiB aggregate.
Maximum decoded pixel bytes: 64 MiB per image; 256 MiB aggregate.
Maximum inflated scanline bytes: calculated per image as height × (1 + width × 4), capped at 64 MiB + 4096 bytes for one maximum-size image.
Maximum aggregate inflated scanline bytes: 257 MiB.
For accepted RGBA8 non-interlaced PNGs, compute those values with checked integer arithmetic from IHDR before decompression. Reject an image or aggregate that exceeds any limit. Stream zlib output with an explicit output cap; do not allocate an unbounded decoded buffer. Require exactly the calculated decompressed byte count and validate every row’s filter byte is in the PNG-defined range 0–4. This counts the filter byte separately from decoded pixel bytes.

Validate signature, IHDR, chunk lengths/bounds, CRCs, ordering, required IDAT, and a zero-length IEND that ends exactly at EOF. Reject invalid dimensions, malformed/truncated zlib data, invalid scanlines, unknown critical chunks, and unexpected trailing bytes. Package the original PNG bytes; do not re-encode or add compression.

6. Planet-source migration and retry behavior
Migrate the five public PNGs to mirrored paths under private/assets/Planets/, subject to resolution of the two unused files’ registry entries.

The migration must:

Inventory source paths, exact casing, byte counts, and SHA-256 hashes.
Inspect every destination before copying.
Stage each copy separately under a unique temporary directory outside private/assets/.
Flush/close staged writes, then verify exact byte count and SHA-256 against the unchanged public source.
Publish with no-overwrite semantics only after verification.
Retry rules:

If the final destination already exists with exact expected bytes and hash, accept it as already migrated without writing over it.
If the final destination exists but differs, stop and preserve it.
An incomplete or partial temporary copy is never a completed migration and is never published as if verified.
A crash-left staging path is reported and left untouched unless its ownership and safe cleanup are unambiguous. A retry uses a new unique staging path.
Public PNG sources are never removed or modified; the 31 private SVGs and their public copies remain unchanged.

8. Publication journal, commit, and recovery
Use a durable write-ahead transaction journal at a fixed repository-root location, for example .asset-package-transaction.jsonl, and add only that exact path to .gitignore. Do not put journal data under public/. Use exclusive creation, append-only transaction records, and flush each journal update to disk before the filesystem operation it authorizes. Output temp files are also flushed and hash-verified before publication. This is crash recovery, not a claim of multi-file crash atomicity.

The journal records:

Transaction ID and stage/state.
Every affected output destination.
Prior existence and SHA-256 for each prior file.
Exact transaction-owned temp and backup paths.
Expected new output hashes.
Pending stale-output retirement paths, with prior hashes.
Prior and expected new manifest hashes.
Whether the new manifest has been committed.
Before beginning, validate the prior generated manifest and hashes. Refuse to overwrite any existing target not proven packager-owned by that prior valid manifest. Record the old nested public/assets/Ships/ships.bin as a pending stale retirement based on the prior manifest; do not depend on the new manifest to identify it.

Publication order:

Create journal with the complete transaction plan and flush it.
Write, flush, and verify all new bundle/schema temp files.
Replace/backup existing outputs according to recorded hashes; publish bundles and schema.
Publish the new manifest last. Its expected hash is the commit marker.
Only after the new manifest is verified, retire the specific old Ships bundle by moving it to its journaled backup path.
Verify all new outputs and the committed manifest, clean only transaction-listed backups/temps whose hashes and state match the journal, then remove the journal last.
Recovery runs before ordinary packaging:

If the current manifest hash equals the expected new hash, treat the output set as committed; finish only journaled stale retirement/cleanup after verifying exact paths and hashes.
If the current manifest is still the prior hash (or prior absence), roll back to the prior set using only journal-listed backups and verified hashes. This handles interruption after publishing schema 1.1 but before publishing manifest 1.1.
If a destination, backup, temp file, or manifest matches neither the recorded prior nor expected-new state, stop and report ambiguity; do not guess or overwrite.
Never wildcard-delete bundles or temporary files. Report orphan temp/backup files not described by a valid journal and stop for review.
A clean-clone path with private/ absent is strictly read-only. If it finds an unfinished journal or ambiguous transaction artifacts, it reports failure and requests recovery in source-available mode; it does not repair or remove files itself.
This journal allows recovery from handled failures and common process interruptions, but cannot promise power-loss durability beyond filesystem guarantees. If filesystem state cannot be reconciled exactly with journal hashes, preserve all files and require manual review.
